How I Structured My Claude Code Setup: Skills, Agents, Hooks, and Workflows

Telling an AI agent to "be careful" doesn't scale. Under enough context pressure, an instruction is a suggestion — the model will route around it with perfectly good intentions. After hitting this pattern one too many times, I decided to stop relying on prose and start enforcing rules in code.

The result is a Claude Code plugin that packages my entire development pipeline: eight skills that define what Claude can do, five specialized agents that each own a single job, four hooks that block rule-violations at the shell level before Claude can execute them, and a set of shared convention files that all agents read from. None of it is clever. The goal is that every non-negotiable rule is enforced, not requested.

This post walks through how it's structured and why each piece exists. The full plugin is on GitHub.

The Core Idea: Enforcement Over Suggestion

There are three layers in this setup, and it's worth being clear about what each one does:

  • Conventions — shared markdown files that all agents read. These define what "correct" looks like for security, style, git, state management, and testing. They're the single source of truth.
  • Skills and agents — procedures and subagents that follow those conventions. Skills define the steps; agents own specific roles.
  • Hooks — Python scripts that fire before any shell or file write. If the command violates a rule, the hook returns a deny decision the model cannot argue with.

The hooks are what make the rest of it credible. Without them, every rule is still just text — something the model might forget or reason its way around.

Skills: Repeatable Procedures

A skill is a SKILL.md file that loads when its description matches a task. I have eight:

ship-feature

The main pipeline. Nine stages, in order:

  1. Create a feat/ branch in its own git worktree — the current folder never changes branch
  2. Run detect-stack.py to discover what verification commands actually exist
  3. Launch code-writer and test-writer in the same message so they run in parallel
  4. Run exactly the commands Stage 2 reported — never assume anything that wasn't found
  5. Run code-quality-reviewer and ui-checker simultaneously
  6. Decide whether there are issues
  7. Fix loop capped at 3 attempts: debugger diagnoses → code-writer fixes → back to verification
  8. Diff review, commit, rebase, push with --force-with-lease --force-if-includes
  9. Second review against the rebased branch — what the PR will actually show

Stage 9 hands off a gh pr create command and stops. Claude never opens the PR.

fix-bug

Lighter than ship-feature. The key rule: if debugger can't reproduce the bug, stop. Don't implement a fix for a cause nobody confirmed. Also: the fix must not weaken or delete any existing test. A failing test is a signal, not an obstacle.

refactor

Records the baseline before touching anything. Before starting, Claude must name the specific risk in one line — "if you can't name it, you don't understand the code yet." The codewriter changes structure, not behavior, and flags bugs it finds rather than fixing them inline.

git-workflow

The procedural companion to conventions/git.md. Always finds the base branch by running default-branch.sh — never assumes main. Covers worktree creation, rebase safety, when to push, and how to clean up.

commit-message,  diff-review,  dev-verify,  env-doctor

commit-message: single line, type: summary, no body, no AI attribution. The hook enforces this — it's not optional.

diff-review: a pre-commit checklist covering security (reads from conventions/security.md), correctness, performance, and scope. If nothing is found, it says so explicitly — silence reads as "not checked."

dev-verify: starts the dev server, hands the user a specific checklist. Does not drive a browser, does not describe what the page looks like. Anything it said about appearance would be invented.

env-doctor: diagnoses environment problems — wrong interpreter, unactivated venv, lockfile drift. Notably: never cat .env into the conversation. Only reads key names.

Agents: Separation of Powers

Each agent owns one job. The reviewers and debugger have no Write or Edit tools — this is enforced by both their tool configuration and a hook. The reason is deliberate:

A reviewer that can edit quietly fixes what it finds, and the finding never reaches the user.

code-writer

Full read/write access. Reads the codebase before writing anything. Implements the smallest correct change. Never weakens a test to make it pass.

code-quality-reviewer

Read-only. Reads conventions/security.md, conventions/code-style.md, and conventions/state-and-data.md as its authoritative source before reviewing. Outputs a verdict with blocking issues and suggestions.

debugger

Read-only. Must reproduce the bug before proposing a fix. If it can't reproduce, it says so explicitly — a clearly-labelled "I couldn't reproduce this" is worth more than a confident guess presented as a fix.

test-writer

No Bash tool. No memory. Cannot read the implementation — by design. A test derived by reading the code asserts what the code does, including its bugs. It works only from the spec, launched in parallel with code-writer.

ui-checker

Read-only. Cannot see the UI and does not pretend to. Reviews what the code says about layout, responsiveness, accessibility, and state coverage. Produces a "Needs visual confirmation" checklist for the user.

Hooks: The Real Enforcement Layer

Hooks are PreToolUse scripts that fire before Claude executes a shell command or file write. They return a deny decision if the command violates a rule. There are four:

Hook What it blocks
check-commit-msg.py Commits to the base branch, multi-line messages, missing type prefix, bodies via -F or heredoc, command substitution in the message
guard-push-main.py git push targeting the base branch, including --all, --mirror, and explicit refspecs
guard-merge-main.py git merge that would land on the base branch. Tracks the destination, not the argument. Allows --abort and --continue.
guard-agent-writes.py Read-only agents (code-quality-reviewer, debugger, ui-checker) writing outside their own memory directory. Path traversal resolved with os.path.realpath before comparison.

All three git hooks are built on a shared _gitcmd.py library that parses compound shell commands, handles cd x && git commit patterns, and tracks branch state across a git switch. They all fail open: if a command can't be parsed, the operation is allowed rather than blocking everything.

Conventions: One Source of Truth

The convention files are what all agents read. The key design principle is that no agent should carry its own opinion about what "correct" looks like — it should read the shared file and apply that. When the rule changes, it changes in one place.

  • security.md — SQL injection, XSS, command injection, path traversal, secrets in logs, auth posture. Shared by diff-review and code-quality-reviewer.
  • git.md — worktrees over branch switching, no commit bodies, base branch detection, rebase safety, push flags.
  • code-style.md — optimized for skimming, less code is better, match the codebase before your own defaults, one error-surfacing convention per app.
  • state-and-data.md — cache is state, optimistic updates belong in the mutation not the component, no update without a rollback, multi-doc writes use transactions or batches.
  • testing.md — report exactly what ran. Never say "tests pass" when no test runner exists. Never weaken a test to make it pass.
  • refactoring.md — record the baseline first, name the risk before starting, change structure not behavior, ask before large deletions or API-shape changes.

Scripts: What Actually Exists

Two scripts underpin the whole pipeline:

detect-stack.py

Returns JSON describing what verification commands the project actually has. Detects Node, Python, Rust, Go, Ruby, and Java. Reads package.json scripts to avoid treating the npm test placeholder as a real runner. If no test runner is found, it appends:

"Do not claim tests passed — report exactly which checks ran."

Every skill that runs verification calls this first. No assumed commands.

default-branch.sh

Finds the base branch from most to least authoritative: remote HEAD symref → local config → network query → probing conventional names. Exits 3 rather than guessing when more than one conventional name exists. The git hooks treat exit 3 as ambiguous and fail open. Every skill that references the base branch runs this script first.

Installing It

The plugin installs via the Claude Code plugin marketplace: 

/plugin marketplace add abigaylehickey/claude-workflow-plugin

That pulls the skills, agents, hooks, conventions, and scripts into your project's .claude/ directory. The README includes a recommended CLAUDE.md drop-in that wires the skills into your project's instructions.

What This Looks Like in Practice

When I start a new feature, I type /ship-feature and describe what I want. Claude creates a worktree, probes what checks exist, launches the code-writer and test-writer in parallel, verifies, reviews, and hands me a gh pr create command. I open the PR. I don't merge from the agent side — ever.

When something breaks, I use /fix-bug. The debugger has to reproduce it before proposing a fix. If it can't, it says so. That single rule has saved me from a lot of confident-but-wrong patches.

The part I use most is actually the simplest: the commit hook. Every message that doesn't match type: summary on a single line gets denied. After a few weeks of that, single-line commits just become the habit.

None of this is magic. It's just rules in code instead of rules in prose — and that small distinction turns out to matter a lot.
